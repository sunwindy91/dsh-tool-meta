# 设计：一个跑在官方 seam 上的自进化闭环

> 一句话：**agent 的每次"翻车"都是一次免费的训练信号**——观测它、反思它、把方法论沉淀成下次能自动加载的 SKILL，再用效果账本决定留谁。

## 一、为什么做这个

Agent 的失败通常是**复现性很强**的：同一个工具名写错、同一类 schema 字段乱填、同一种协作冲突（stale version），会在不同会话里反复出现。
但这些失败目前大多止步于"这一次重试成功"，**没有变成资产**。本插件要验证的问题是：

> 能不能只用官方提供的接口（事件 + 文件系统），把"失败 → 方法论 → 自动滋养"这条链路接通，并且**可审计、可回滚、可复现**？

## 二、闭环的四个算子（演化机器）

| 算子 | 含义 | 本插件的实现 |
|---|---|---|
| **变异** | 失败产生新个体 | 观测 `tools/result` 失败 → 规则反思 → 生成新 SKILL（同签名去重） |
| **选择** | 按效果保留 | 效果账本 `trials`（复发次数）/`successes`（被复用后成功次数） |
| **遗传** | 把能力传给下一代 | `manifest.json` 能力盘 + `meta_search` 关键词检索 |
| **繁殖** | 下一代自动获得能力 | DSH `skill-filesystem` 自动发现 `<root>/<id>/SKILL.md`，**无需任何额外代码** |

四个算子**全部实现**，且都跑在官方接口上——这是本插件与"自己造一套记忆格式"的做法的根本区别：**零私有格式**。

## 三、数据流（一次翻车的完整生命周期）

```
工具调用失败
   │  ctx.on("tools/result")                     ← 官方事件 seam（冻结终态）
   ▼
reflector.reflect(exec, result)                  ← 规则模板（确定性，LLM 增强留了口子）
   │  ├─ 命中负向清单（环境噪音）→ 丢弃，不沉淀
   │  └─ 分类：UNKNOWN_TOOL / TOOL_OUTPUT_ERROR / 协作冲突 / 通用
   ▼
计数闸门：同签名连续失败 ≥ 阈值（默认 2）才真正沉淀
   │
   ▼
skillwriter.writeSkill()                         ← 官方文件系统 seam
   │  ├─ 已存在 → trials+1（复发）+ audit("recur")
   │  └─ 新建   → 写 <root>/<id>/SKILL.md + 刷新 manifest + audit("precipitate")
   ▼
下次会话：skill-filesystem 自动发现 → agent 自动带上这条教训（滋养）
   │
   ▼
被复用后不再翻车 → updateSkill(successes+1) → audit("verify")
```

**关键点**：`successes` 只在"这条教训被用上、且没有再次失败"时 +1；它不是"成功率分母"，而是一个**被验证次数**的计数。这一点在 `docs/observation.md` 里专门写了，避免被误读。

## 四、单一真相源与目录布局

```
<META_SKILLS_DIR | ~/.dsh/skills>/
├── <skill-id>/SKILL.md          ← 单级布局：DSH 单级扫描规则要求 <root>/<dir>/SKILL.md
├── manifest.json                ← 能力盘（文明遗产清单，随账本刷新）
└── .audit/ledger.jsonl          ← append-only 审计流水（沉淀/复发/验证/归档/恢复）
```

**为什么是单级**：多层命名空间（如 `<root>/<tool>/<id>/SKILL.md`）会让官方发现机制扫不到，滋养链路直接断掉。
代价是 id 必须自带命名空间（`learn-unknown-tool-<hash>`、`learn-collab-<hash>-<hash>`），这一点是有意为之。

## 五、明确不做（Non-goals）

- **不做向量库/自建记忆格式**：一旦自建格式，就不再能声称"跑在官方 seam 上"，可复现性也没了。
- **不沉淀环境噪音**：缺凭据、沙箱策略拒绝这类失败，学了也没用，反而污染能力盘（见 `docs/governance.md` 负向清单）。
- **不自动删除**：只归档（`.archive/`），可恢复。
- **不做"成功率仪表盘"**：`trials/successes` 的语义不足以支撑成功率，宁可不做，也不做一个会被误读的指标。
- **不替 agent 做决策**：插件的产物是**候选方法论**，采信与否由下一次调用是否成功来投票。

## 六、已知局限

1. **只在失败时学习**：顺利执行的任务不产生新教训——长期看数据会平线（观测数据里 09-03 至 09-09 五天平线就是这个形态）。
2. **规则模板的泛化上限**：反思目前是确定性模板（不调 LLM），覆盖面靠分类表；未覆盖的失败落到"通用"分支，方法论质量较粗。
3. **观测长度不足**：13 次快照、单机、无对照组，**不能**用来证明能力提升（边界写在 `docs/observation.md`）。
4. **阈值是猜的**：`META_FAIL_THRESHOLD=2` 没有实验依据，只是"单次失败多为偶发"的直觉。


## 七、从"事后反思"到"事前闸门"（v0.4）

### 一个真实暴露的盲区

维护者在整理自己的历史文件时，用**通配符**批量删除，范围超出了原定计划——删掉了几份不在归档计划内的文件。
复盘时发现两件事：

1. **删除操作在工具层全部成功** → `tools/result` 没有失败 → **本插件的学习闭环根本没被触发**；
2. 因此这类"**成功但错误**"的动作，**在原理上无法通过"从失败中学"来防范**——没有失败可反射。

### 结论：两类错误，要两套机制

| 错误类型 | 有无失败信号 | 用什么防 |
|---|---|---|
| **操作层**：工具怎么用才对（工具名、schema、协作冲突） | 有（`isError`） | **事后反思 → 沉淀 SKILL**（v0.1–v0.3 已实现） |
| **判断层**：该不该做这件事（不可逆、超出范围） | 无 | **事前闸门**（v0.4 新增）：`ctx.tools.guard` + `meta_prepare` 声明 |

### 设计取舍

- **不做"禁止一切删除"**：那只会让人关掉闸门。做法是**把不可逆动作变成"必须先声明"**——声明里有目标清单、备份位置与哈希，并被写进审计流水。
- **通配符与受保护路径不可豁免**：这两类是本次事故的直接成因，任何声明都不能放行。
- **代码型删除单独一类**：这类调用的目标在运行时才算出来，源码里抽不出可靠清单；若按"显式删除"处理，
  会要求一份对不上的清单，闸门就永远过不去。故单独要求 `scope + expected_count + backup_hash`。
  **这个分类顺序是被测试逼出来的**——先用"抽得到路径就算显式"的逻辑，结果代码型用例直接被误判（单测抓出，见 `tests/unit.mjs` 闸门组）。
- **闸门是单调的**：DSH 的 guard 一旦返回拒绝理由，后续监听器无法翻案——这保证了"闸门不会被下游悄悄放过"。

### 已知局限

1. **拦不住精心绕过**：把目标藏在运行时计算、或分多步执行，闸门识别不了。它的定位是"提高不可逆动作的成本并留下痕迹"，不是"保证安全"。
2. **规则是样本驱动的**：删除信号表来自已知模式（CLI 命令 + 常见语言 API），新工具/新写法需要补表。
3. **声明 ≠ 校验**：闸门检查"有没有声明"，**不检查"声明的备份是否真的存在"**——`backup_hash` 目前只入账，不做实际比对（下一步可接 `post-execute` 校验）。


### 第二种失败模式：闸门必须限定作用域（v0.4.1）

上面那类错误是"**漏判**"（把代码型删除误当显式删除）。上线后立刻遇到相反的一类：**误判成灾**。

作者在**给这个闸门写文档**时，被自己的闸门拒绝了一次——因为那份文档**内容里讨论**了删除命令的写法。
紧接着，写构建脚本时又被拒了一次：脚本里出现了删除 API 的片段。
第三次更隐蔽：子 agent 的提示词里包含删除命令示例，同样被拒。

**根因有两条：**

1. **没有工具作用域限定**：闸门检查**所有**工具调用的参数。可是 `write` / `edit` 的参数是"要被写下来的文本"，
   文本里合法地讨论删除命令，与"执行删除"是两回事。**一个会拦住写文档的闸门，结局一定是被卸载。**
2. **一条正则匹配裸命令词**：目录删除命令词不带任何 API 前缀也会命中，导致"脚本里出现该词即被拦截"——
   而这正是描述这个缺陷本身所必需的词。

**修复**：
- 增加**内容型工具跳过表**（`write` / `edit` / `apply_patch` / …），并支持 `META_GATE_SKIP_TOOLS` 追加；
- 回归用例 4 项锁定两个方向：**内容型工具不被拦** + **动作型工具仍然被拦**（放宽作用域不能把闸门放空）。

**教训（比修复本身更值钱）**：
> 检测器的**两个方向**都可以毁掉它——**漏判**让闸门变成装饰，**误判**让闸门被关掉。
> 而"误判"这一侧在开发期几乎测不出来，只有**真的用它**才会暴露：作者是在用自己写的闸门干活时被拦了三次才发现的。


## 八、去碎片化：教训也会"越攒越没用"（v0.4.2）

### 现象（实测）

上线一段时间后巡视能力盘发现：**同一个 `edit` 工具积累了 8 条教训**——
每条的失败消息不同（文件版本过期 / 写入被占用 / 未先读取…），于是按"完整消息哈希"生成的 id 各不相同，
**同一种失败被拆成多个条目**。后果不是"硬盘不够"，而是：

1. **检索被稀释**：`meta_search("edit")` 返回一堆近义条目，真正有用的那条排在后面；
2. **账本被切碎**：trials/successes 分散在多条上，单条看起来都"证据不足"——而它们本来是同一条经验；
3. **阈值失效**：阈值按"同签名连续失败"计数，签名一碎，"第 2 次才沉淀"的保护也形同虚设。

### 两个动作

1. **沉淀时归一到"错误类"**：把失败消息里的路径/数字/引号/十六进制抹成占位符（`<path>` / `<n>` / `<str>` / `<hex>`），
   再按 `tool + 错误类` 生成 id。同一种失败不再因路径不同而分家。
2. **`meta_compact` 整理历史存量**：按 `tool + 错误类` 分组，组内选账本最厚的一条做 canonical，
   **账本累加**（trials/successes 求和）、写入 `merged_from: [...]` 记录合并来源，
   **其余条目归档而非删除**（可 `restore`），并写审计 `compact`。

### 取舍与局限

- **不做相似度合并（不引 embedding）**：本插件的立场是零依赖 + 确定性。`错误类` 是**保守的**归并——
  它只合并"看起来就是同一件事"的条目，宁可留下少量碎片，也不误并两条不同经验。
  （对比：Ratchet 用 embedding 余弦做去重——更强，但需要模型与外部依赖。）
- **合并是可逆的**：被并入的条目进归档目录而不是消失，`merged_from` 记录了它去过哪里——
  如果合并错了，可以逐条恢复。
- **只处理 `learn-*`**：人工维护的教训（人工 SKILL）不参与自动合并。


### 真实数据上的第一次运行，当场暴露了语义问题（v0.4.3）

把去碎片化**第一次跑在真实能力盘上**（17 条 → 13 条，3 组合并、4 条归档），立刻发现一个问题：
`learn-collab-*`（协作冲突，正文含"并行写文件前先 read、先划互不重叠的写入域"这段**独立建议**）
因为**失败类相同**，被并进了一条普通的"调用失败"教训。

**根因是一条被忽略的假设**：按"失败类"合并的前提是"**同类失败 ⇒ 同类建议**"——这在真实数据上不成立。
两类失败可以有同样的报错文本，但值得留下的**指导完全不同**。

**规则收紧**：只合并**通用型**教训（id 形如 `learn-<12hex>-<12hex>`）；
专类教训（`learn-collab-*` / `learn-output-schema-*` / `learn-unknown-tool-*`）**不参与自动合并**。

**被误并的条目已从 `.archive/` 恢复**——"归档而非删除"这条治理规则在真实场景里第一次派上用场：
**如果不是归档而是删除，这次修正就只能靠备份手工重建。**

### 三条关于"自动整理"的教训

1. **整理规则本身需要测试**：合并逻辑跑了 6 个单测全绿，但真实数据一跑就出语义问题——
   因为单测造的是"同工具同类失败"，而真实数据里有"同类失败但不同建议"的条目。
2. **保守比聪明重要**：宁留碎片也不误并。误并会**静默降低能力盘质量**（检索还在返回结果，只是返回的是错的那条）。
3. **可逆性是整理功能的前提**：任何自动整理都必须"归档可恢复"，否则第一次跑错就要靠备份救。
