# 已知拦不住的删除方式（诚实边界清单）

> 为什么要主动写这个：**声称"能拦"很容易，说出"拦不住什么"才让人信。**
> 闸门的检测是**模式匹配**（命令行式 + 常见语言 API），不是标准动作词表。以下是已知漏判。

## 一、已知漏判（会放行，但确实在删东西）

| 方式 | 为什么漏 | 备注 |
|---|---|---|
| PowerShell 的 .NET 静态方法删除文件 | 不是常见 CLI/API 形态 | 例如 `[IO.File]::Delete(...)` 这类调用 |
| `find … -delete` | 删除动作藏在参数里 | 命令行式，但不是删除命令本身 |
| 其它语言的删除 API | 检测表只覆盖了常见几种 | Go / Rust / Ruby / Perl 等未覆盖 |
| 变量拼路径绕过受保护检查 | 受保护判断是**对原始文本做子串匹配** | 路径在运行时才算出来时必然绕过 |
| 分多步化整为零 | 每一步都不像删除 | 例如先移动到临时目录、再整体清空 |
| 覆盖式破坏 | 语义上是"写"不是"删" | 例如把文件截断为 0 字节覆盖掉内容 |
| 通过子进程自己动手 | 动作不经过被守卫的工具 | 与 Permit0 的已知局限同类 |

## 二、已知误判（会拦，但其实是合法操作）

| 情形 | 原因 |
|---|---|
| **文本内容里出现删除命令** | v0.4.1 之前的真实事故（作者被自己的闸门拦了三次）；现已用"内容型工具跳过表"修复，但**新增工具若不在表里仍会误拦** |
| 受保护路径字符串出现在无关上下文 | 受保护判断是原始文本子串匹配 |

| **只读命令里"提到"删除写法** | 真实案例：一条 `pwsh` 命令只是用 `Select-String` **搜索**若干删除写法，却被判为删除动作。根因同 v0.4.1（分不清"提及"与"执行"）。**已修，分两步**：v0.4.1 修内容型工具（write/edit）；**v0.4.5 修动作型工具**——只分析参数的字符串叶子，按语句切段，段首是读/搜/打印类命令就跳过，段首是执行器（python/node/pwsh…）则递归解析内部真正执行的命令 |

## 三、这道闸门的真实定位

它**不是**安全边界，而是一道**流程闸门**：

- **它保证**：不可逆的文件删除**必须留下可审计的声明**（删什么、依据哪份备份、哈希多少），而且声明一次性；
- **它不保证**：拦住所有删除（见上表）。

如果要往"边界"方向走，下一步应该是**标准动作词表 + 归一化**（把任意工具调用映射到 `file.delete` 这类规范动作），
而不是继续加正则。这条已经在生态里有人做（见 `docs/design.md` 的行业位置调研），属于下一阶段的事。
