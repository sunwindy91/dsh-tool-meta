# 稳定性边界与母体收益（本项目的"什么时候算完工"）

> 这份文档回答两个问题：
> 1. **它什么时候算稳定？**（工程判据）
> 2. **它有没有在助益母体？**（存在理由）
>
> 结论先行：**稳定性是前置条件，母体收益才是目的。**
> 一个"从不报错但没改变任何东西"的插件，等于零。

---

## 第一部分：稳定性边界

### 1.1 先纠正一个常见误解

"一直在出问题" ≠ "质量差"。本项目 v0.1 → v0.4.5 的六次变更里：

| 版本 | 性质 | 谁发现的 |
|---|---|---|
| v0.4 闸门 | **新能力** | 主动设计 |
| v0.4.1 内容型工具误报 | 修 bug | **真实使用**（写自己的文档时被拦） |
| v0.4.2 去碎片化 | 新能力 | **观察真实能力盘**（同一工具 8 条同类教训） |
| v0.4.3 语义误并 | 修 bug | **真实数据第一次运行** |
| v0.4.4 账本不可复现 / 声明可无限复用 | 修 bug | **主动审计 + 先写测试** |
| v0.4.5 只读命令被拦 | 修 bug | **真实使用**（搜索删除写法时被拦） |

**六次里四次是"用起来才发现"。** 这个分布本身就是答案。

### 1.2 三条根因（按深度排序）

| # | 根因 | 说明 | 能否消除 |
|---|---|---|---|
| 1 | **判断没有形式化定义** | "这次调用是不是在删除"没有封闭解：是命令文本？是执行意图？还是实际效果？任何规则都只是开放集合的**近似** | ❌ **不能**，只能降低暴露率 |
| 2 | **消费两种可靠性不同的资源** | ① 宿主官方信号（`tools/result`、guard 语义、技能自动发现）——稳定；② 自己写的启发式（检测表、错误类归一、合并规则）——**必须随真实数据演进**。出问题几乎都在 ② | ⚠️ 可隔离：把 ① 与 ② 在代码与文档里分开 |
| 3 | **反馈延迟** | 这类 bug 只有真实使用才暴露，而使用不可预测 → **修 bug 的速度取决于使用强度，不取决于代码质量** | ❌ 不能，但可以用"高强度自用"加速 |

### 1.3 最终态：对一半可以，对另一半永远没有

| 部分 | 能否到最终态 | 依据 |
|---|---|---|
| 宿主接缝（事件订阅 / 工具注册 / guard 注册 / 目录布局） | ✅ **可以** | 官方接口不变则不会坏；已有"宿主升级后跑全部测试 + 全链路验证"的流程 |
| 治理不变量（归档而非删除 / 声明一次性 / 账本 append-only / 可回退） | ✅ **可以** | 语义明确、可测试、不依赖外部世界的模糊性 |
| 检测与分类启发式 | ❌ **永远在演进** | 输入开放 + 语义模糊 |
| 效果声张（"它让 agent 变强了多少"） | ❌ **不应声称稳定** | 单机、样本小、无对照组 |

### 1.4 四条可检验的稳定判据

**稳定 ≠ 零 bug。稳定 = 下面四条同时成立：**

| 判据 | 含义 | 当前状态 |
|---|---|---|
| **A. 接口稳定** | 依赖的宿主接缝有**版本验证记录** | ✅ 有 |
| **B. 不变量被测试锁住** | 承诺的性质永远为真，而非"我记得写了" | ✅ 有（测试里此类断言占多数） |
| **C. 失败必留痕** | 任何失败**可见**（日志结果码 / 心跳告警 / 审计流水） | ✅ 有 |
| **D. 一切可回退** | 自动改动都能撤销（归档而非删除 / 合并来源可追 / 版本历史） | ✅ 有 |
| **E. 边界被公开声明** | 明确写出**不保证什么** | ✅ 有（`known-evasions.md`） |

### 1.5 停止线：什么时候算"够了"

1. **不变量类断言全绿** —— ✅ 已满足
2. **连续真实使用只暴露"新输入形态"，不再暴露"违反自己承诺的不变量"** —— ✅ 基本已满足
3. **"保证什么 / 不保证什么"已写进文档** —— ✅ 已满足

**超出这条线的工作（例如把检测升级为标准动作词表 + 归一化）属于另一个量级的产品，不在本项目目标内。**
这条界限本身就是"边界被公开声明"的一部分。

## 第二部分：母体收益（存在理由）

### 2.1 为什么它才是目的

- **稳定性**：保证它**不被卸载**（不稳定 → 归零）。
- **母体收益**：保证它**值得存在**（没收益 → 只是个没坏的工具）。

> **目标函数：母体收益 ≈ 被母体采纳的改动数 × 采纳的持久度**
> 分母里没有"功能数"，也没有 star 数。

### 2.2 三条通道（"怎样界定"的答案）

| 通道 | 含义 | 可核验信号 | 当前级别 |
|---|---|---|---|
| **A. 对内进化** | 从失败沉淀经验 → 后续会话自动继承（助益母体的**运行时**） | 技能被宿主自动发现并在新会话可用；账本持续变化 | ✅ **已成立**（同一目录下的技能会被官方机制自动继承） |
| **B. 对外反哺** | 把使用中的发现变成**母体自身的改动** | 官方变更日志/提交里出现对应修复；插件被官方收录；建议被写进官方文档 | ⚠️ **只到"被确认"，未到"被采纳"** |
| **C. 模式层** | 母体或生态采纳了**规矩**（前置声明 + 单调拒绝 + 同账审计） | 其他仓库/文章独立复述并使用该模式 | ❌ **无** |

### 2.3 信号分级（哪些算，哪些不算）

| 级别 | 信号 | 是否作为判据 |
|---|---|---|
| 弱 | star、下载量、文章阅读量、点赞 | ❌ **不算**（易自嗨） |
| 中 | 官方回应并**源码级核验**、issue 被引用、插件被收录 | ✅ 算 |
| 强 | **官方据此改了代码**；有团队按该模式实现自己的版本 | ✅ 算（这是目标） |
| 终局 | **你不在场时它仍在产生价值**（别人用、被引用、经验被继承） | ✅ 算 |

### 2.5 判断句

> **目前的真实状态：B 通道"被确认"（官方源码级核验 3 条），但尚未"被采纳"（没有证据表明母体据此改了代码）。**
> **要把 B 从"被确认"推进到"被采纳"，只有两条路：** ① 核实母体的变更记录里是否已包含那些修复；
> ② 让插件本身变成母体可安装、可引用的东西（进入生态）。
> **C 通道（模式被采纳）目前为零，而有文章可发——这是当下性价比最高的一件事。**
